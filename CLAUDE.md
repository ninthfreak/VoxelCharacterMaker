# Project: voxel character system (Godot 4)

Read `SPEC.md` before any work; it holds every decision made so far. If something there seems wrong, raise it rather
than silently changing course.

## Working with the owner
- They assess risk and tradeoffs themselves. Give accurate feasibility reads, keep uncertainty visible, rate
  difficulty and confidence explicitly, and state recommendations as recommendations, never as decisions.
- Ask when a choice is genuinely theirs (style, look, scope). Make the call on routine engineering.
- They are red/green colour blind, dyslexic and have ADHD: no red-vs-green-only signals in UI or debug views, short
  clear labels, readable text, summaries before detail.
- Show visual results (screenshots/renders) for anything that changes how characters look.

## Conventions
- Engine: current stable Godot 4.x, GDScript. The character assembly code (body + head + face + worn items -> parts,
  voxels, meshes) exists exactly once and is shared by the game and the editor.
- Voxel data uses the asset axes in SPEC.md §2 (x width, y depth with front at -y, z up, 24 voxels per metre); convert
  to Godot space only at mesh-building time, through one function.
- Asset JSON under `assets/` is generated by `tools/build_bodies.py`; regenerate rather than hand-edit.
- Tests run headless (`godot --headless ...`); every acceptance check in SPEC.md §12 should become an automated test.
